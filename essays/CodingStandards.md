## Why Coding Standards Matter More Than You Think

When most people hear the term “coding standards,” they immediately think of indentation rules, semicolons, or whether curly braces go on the same line or the next. Those details can feel trivial. But after working with ESLint in VSCode this past week, I’ve started to see coding standards as something much more impactful. They are not just about style—they’re about discipline, learning, and writing code that can stand the test of time.  

### My First Week with ESLint

At first, ESLint felt like a strict teacher breathing down my neck. Every squiggly red underline felt like a slap on the wrist. Fixing error after error was frustrating and slowed me down. But as I kept working, I realized something important: ESLint wasn’t just nitpicking—it was teaching me.  

For example, it reminded me when I forgot to declare variables with `let` or `const`. It pushed me to use consistent naming conventions and to avoid unused imports. Over time, I noticed I wasn’t just fixing errors—I was learning better habits. The corrections became automatic. What seemed “painful” at first was actually useful training.  

### Coding Standards as a Learning Tool

What surprised me is how coding standards can actually help you learn a programming language. ESLint is basically a constant feedback loop—it shows me not only that something is wrong, but also why it’s wrong and how to fix it. By repeatedly encountering and fixing these issues, the rules start to stick in my brain. I’m internalizing best practices in a way that just reading a style guide could never accomplish.  

This makes me think that coding standards are not just about making code look pretty for others. They’re also about making me a better programmer. It’s like learning grammar in a new language: at first the rules are annoying, but eventually they help you write with clarity and confidence.  

### Why Standards Improve Quality

Beyond personal growth, coding standards also make collaborative projects much smoother. When everyone follows the same style, the codebase feels unified, no matter how many people worked on it. That makes debugging, reviewing, and adding new features less confusing. Instead of fighting through five different coding “dialects,” I can focus on what the code actually does.  

Coding standards also reduce “friction.” A code review should be about logic and design, not about whether a teammate used tabs instead of spaces. Standards eliminate those distractions.  

### Final Thoughts

At first, I thought coding standards were mostly about aesthetics. Now, after a week of living with ESLint, I see them as both a learning tool and a quality-control system. They may start out feeling painful, but in the long run, they save time, improve collaboration, and make me a stronger programmer. If I had to choose one software engineering technique to improve quality, I’d agree with the statement: it would be coding standards.
